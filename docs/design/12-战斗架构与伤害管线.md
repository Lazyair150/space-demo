# 战斗架构与伤害管线（现状 / 目标 / 迁移）

> 范围：只谈战斗侧（玩家、敌人、子弹、伤害、生命、状态效果、能力）。
> 工业舱（JarSystem 那套）**不在本文范围**，它有自己的分层和存档边界。

---

## 1. 现状：三套并行的受伤实现

### 1.1 谁调用谁（实际代码，2026-11-19）

```
玩家开火
  Player._shoot()                        scripts/player/Player.gd:88
    └─ b.set("damage", attack_damage_int())        # 永久成长 × 临时修正，已取整
    └─ 子弹进入场景

玩家子弹命中
  PlayerBullet._consume_hit(node)        scripts/PlayerBullet.gd:26
    └─ _try_hit(node)                    :36
        └─ if node.has_method("take_damage"): node.take_damage(damage)   # 鸭子类型

敌人子弹命中
  EnemyBullet._on_body_entered(body)     scripts/EnemyBullet.gd:13
    └─ if body.is_in_group("player") and body.has_method("take_damage"):
           body.take_damage(damage)                                     # 组判定

追兵接触
  EnemyChaser._physics_process           scripts/EnemyChaser.gd:29
    └─ other.take_damage(contact_damage)
    └─ died.emit(); queue_free()          # 撞到玩家后自己也没了

追击/射击的敌人受伤
  EnemyChaser.take_damage(amount)        :44   → hp -= amount → score + 爆炸 + died + free
  EnemyShooter.take_damage(amount)       :57   → hp -= amount → score + 爆炸 + died + free

玩家受伤（唯一带规则链的一处）
  Player.take_damage(amount)             scripts/player/Player.gd:69
    ├─ if _invuln > 0: return            :71
    ├─ if features.try_block_damage(...) :74   # 能量盾，抵挡后自己关掉
    ├─ hp = max(0, hp - amount)          :77
    ├─ GameState.report_player_hp(hp)    :78   # 往全局状态广播
    ├─ _invuln = invuln_time             :79
    └─ damaged / died 信号 + 闪光 + 音效
```

中毒（Buff）走 `take_damage`，因此**自动吃玩家的无敌窗口和护盾**——这是现状里唯一"规则被复用"的地方，也是它没法复用到敌人身上的原因：敌人没有 `_invuln`，也没有 `features`。

### 1.2 数据流：所有伤害都是 `int`

```
攻击载体 ──(int amount)──▶ 目标的 take_damage(amount) ──▶ 目标内部扣 hp
```

一次伤害里**没有**：谁打的、什么类型、命中点、能不能触发暴击/吸血/反伤、这次伤害最终结算成多少。

### 1.3 归属：hp 与死亡逻辑散在三个脚本里

| 对象 | hp 字段 | 受伤实现 | 死亡处理 | 分数 |
| --- | --- | --- | --- | --- |
| 玩家 | `Player.gd:27` | `take_damage` + 无敌 + 护盾 | 信号 + 爆炸 + free | 不参与 |
| 追兵 | `EnemyChaser.gd:12` | 直接扣 | 爆炸 + `died` + free | `+score_value` |
| 射手 | `EnemyShooter.gd:16` | 直接扣 | 爆炸 + `died` + free | `+score_value` |

也就是说：**"扣血—判定死亡—发奖励—播反馈"这四件事，三份实现各写了一遍**，而玩家那一份还额外混进了防御规则。

## 2. 现状的五个真问题（按危害排序）

1. **目标识别规则有两套**：玩家子弹用"有没有 `take_damage`"（鸭子类型），敌方子弹用"是不是 `player` 组"。加新目标时容易一边能打、一边不能打。
2. **伤害没有上下文**：`int` 传不进"来源/类型/命中点"，中毒与子弹伤害在目标看来完全一样，无法做抗性、减伤、暴击、吸血。
3. **三段重复的生命/死亡逻辑**：任何一次规则调整（比如加"死亡前无敌 0.2 秒""掉落率按伤害来源区分"）都要改三处。
4. **防御规则写死在玩家身上**：`_invuln`、`features.try_block_damage` 都在 `Player` 内部，敌人无法拥有护盾/无敌，组件化收益被锁在一侧。
5. **结算结果不可读**：没有"这次伤害实际扣了多少、被谁挡了多少"的返回值，HUD 飘字、吸血、反伤都只能事后猜。

## 3. 目标结构：三个边界，不是一个大基类

```
┌─────────────────────────── 战斗个体（节点组合，不是继承） ───────────────────────────┐
│                                                                                      │
│  Player / EnemyChaser / EnemyShooter                                                 │
│    ├─ Identity      阵营、标签、显示名           （轻量，Resource 或 Node）           │
│    ├─ Health        当前/最大生命、apply/heal、health_changed、died                  │
│    ├─ Defenses      无敌窗口、护盾（可多个，按顺序问）                               │
│    ├─ Stats         属性修正（已有 StatCalculator）                                  │
│    ├─ Effects       临时状态（已有 StatusEffectManager）                             │
│    └─ 行为脚本      移动 / 射击 / AI（各自不同，**不统一**）                          │
│                                                                                      │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                    ▲
   ① 攻击载体只做一件事：描述这次攻击  │  ② 目标自己决定怎么吃下来
                                    │
   子弹 / 接触 / 毒 / 爆炸 ── DamageInfo ──▶ DamageReceiver ──▶ Health
                                (数据)        (目标侧入口)        (只存生命)
                                                     │
                                                     ├─ 依次问 Defenses：无敌？护盾？
                                                     └─ 产出 DamageResult（实际扣血/被挡）
                                                            │
                                             反馈 / 死亡 / 吸血 / 反伤 / 飘字
```

三条边界（也是三个"只该有一个 owner"的约定）：

| 边界 | 谁负责 | 谁不负责 |
| --- | --- | --- |
| 我是谁、我有什么组件 | 个体节点自己（场景树组合） | 不做统一 `Entity` 父类管行为 |
| 一次伤害怎么被处理 | 目标侧的 `DamageReceiver` + 防御组件顺序 | 攻击方不知道目标内部结构 |
| 生命值归谁 | `Health` 独占，别人只读 | 护盾/暴击/吸血**不写进** `Health` |

### 3.1 最小接口（够用即可，先不铺满）

`Health`（Node）：

```gdscript
signal health_changed(current:int, max_value:int)
signal died(info: DamageInfo)      # 带着"被什么打死"，掉落/计分才有依据

var current:int; var max_value:int
func apply_damage(amount:int, info: DamageInfo = null) -> int   # 返回实际扣除
func heal(amount:int) -> int
func is_alive() -> bool
```

`DamageInfo`（RefCounted，一次攻击的描述）：

```
attacker: Node      # 谁打的（可能为空：陷阱/毒）
source: Node        # 载体（子弹/毒实例）
amount: int         # 攻击方算出的原始伤害
type: StringName    # &"bullet" / &"contact" / &"poison" / &"explosion"
hit_position: Vector2
tags: Array[StringName]   # &"dot" / &"pierce" ...
```

`DamageResult`（RefCounted，结算结果）：

```
requested / blocked(被无敌或护盾全挡) / absorbed(护盾吸收) / hp_damage / died
blocked_by: StringName   # &"invuln" / &"shield" / &"none"
```

### 3.2 兼容策略（关键，避免一次性推倒）

- `take_damage(amount:int)` **保留**为薄适配器：内部构造 `DamageInfo{type=&"legacy"}` 再调 `receive`。
  好处：现有 5 个调用点、13 套测试里的断言都不用立刻改。
- 新代码只走 `DamageReceiver.receive(info)`；旧调用点在迁移表里逐个替换，替换完删适配器。

## 4. 三种做法的取舍

| 方案 | 做什么 | 代价 | 何时合适 |
| --- | --- | --- | --- |
| **A. 只抽 Health** | 三处 hp/死亡合并成 `Health` 组件，`take_damage` 签名不变 | 半天量级；收益=去重、敌人也能有血条；伤害仍无上下文 | 只想止血重复 |
| **B. Health + DamageInfo/Result**（推荐） | A + 目标侧 `DamageReceiver` + 结算结果；`take_damage` 保留为适配器 | 需改 5 个调用点、补测试；收益=暴击/吸血/抗性有了挂点 | 接下来要做命中反馈/暴击/多种伤害 |
| **C. 全套组件化** | 再加 Identity/Defenses/Weapon/Movement 全套 | 大改场景树与测试，收益在"敌人种类 >10"才明显 | 现在不需要 |

推荐 **B，但拆成两步走**：先 A（可独立验收），再 B（只加管线，不动行为）。

### 明确不做

- 不做全局 `DamageManager`：伤害规则属于受击方，全局单例只会变成第二个真状态源。
- 不做 `Entity` 基类统一行为：玩家和敌人的移动/攻击本来就不一样，共同点只有组件。
- 不给每个效果建组件：减速只是 Buff modifier，不需要 `SlowComponent`。
- 不改工厂/存档：本次迁移不碰 `IndustrialRuntime`、不碰 `GameState` 的钱包语义。

## 6. 新增的验收条件（B 阶段）

1. 一次 10 点伤害打到"5 点护盾 + 20 生命"的目标：`DamageResult` 必须是 `requested=10, absorbed=5, hp_damage=5`，盾只是被消耗而不是消失。
2. 无敌期间任何 `DamageInfo` 都返回 `blocked_by=&"invuln"`、`hp_damage=0`，且**毒与子弹表现一致**。
3. 敌人的 `died(info)` 能拿到"被什么打死"；击杀分数仍与 `score_value` 一致，不重复结算。
4. `take_damage(3)`（旧接口）与新接口 `receive(DamageInfo{amount=3})` 结果相同——保证迁移期两套调用不打架。

### 调用链（改造后）

```
PlayerBullet / EnemyBullet / 追兵接触 / PoisonBuffInstance
        → DamageInfo.make(amount, type, attacker, source, hit_position)
        → 目标.receive_damage(info)            # 旧接口 take_damage(int) 保留为薄适配器
        → DamageReceiver.receive(info)
             ├─ Health.is_alive() ? 否则 blocked_by="dead"
             ├─ 防御组件逐个 resolve_defense()：Invulnerability → ShieldDefense
             └─ Health.apply_damage(剩余, info)
        → DamageResult（requested/absorbed/hp_damage/blocked_by/died）
        → 角色做反馈（受伤音效/震屏/飘字）与死亡处理（计分/爆炸/died 信号）
```

### 三个坑（实测）

1. **`hp` / `_invuln` 用属性代理兼容旧读取点**：`tests` 与能力脚本还在读写它们，直接删会破坏 325 项既有断言。现在 `var hp: int: get: return health.current`、`var _invuln: float: get/set` 指向组件，旧代码零改动继续工作。
2. **`Control` 当 `Node2D` 子节点渲染不可靠**：第一版飘字用 `Label`，调试打印显示节点存在、`size 25×39`、`alpha 1.0`、`visible true`，但截图里几乎看不见（只有极淡的痕迹）。改成 `Node2D + draw_string/draw_string_outline` 后立刻可见。以后世界空间文字一律用 `_draw`，不要用 Control。
3. **`DamageResult` 的"被挡"要和"掉血"分开断言**：护盾挡下时 `hp_damage == 0` 但 `absorbed == 1`，只断言"没掉血"会漏掉"到底挡住了没有"。

### 语义变化（有意为之）

- **护盾挡下不再产生无敌帧**：改造前 `take_damage` 被 `try_block_damage` 提前 return，不会设 `_invuln`；现在管线同样如此。但 `EnergyShield` 自己会 `grant_invuln(0.5)`，所以"挡完短暂安全"仍然成立——这是盾的规则，不是管线的规则。
- **毒伤害带 `type = poison`**：将来做"毒抗"时有挂点，现在行为与之前一致（仍然受无敌/护盾约束）。

### 验证

- 新增 `tests/combat_pipeline_smoke.gd` **29 项**：吸收 5/10 → 实际扣 5、护盾耗尽后不再吸收、旧接口同管线、致命与"死人不再受伤"、玩家无敌窗口、毒同受约束、护盾全挡但给盾自带无敌、敌人只发一次 `died`、分数只结算一次、飘字节点生成。
- 全量回归 14 套 **354 项 0 失败**；`--quit-after 180` headless 启动 0 error / 0 leak。
- 截图 `tmp/ui_capture/combat_01_damage_number.png`（敌人头顶橙色 `-1` 带深色描边）、`combat_02_player_hit.png`。

## 11. 扩展实验：暴击 / 吸血 / 敌人护盾（2026-11-19）

三个实验的目的不是加玩法，而是撞现有接口，看 B 路线能不能装下后续需求。**每阶段独立验证，最后统一回归**；没有新建 `CriticalSystem` / `LifestealManager` / 全局 `DamageManager`。

### 11.1 暴击（攻击方判定，请求创建时就定稿）

| 位置 | 做法 |
| --- | --- |
| `DamageInfo` | 新增 `critical: bool`，由 `make(..., critical_ := false)` 写入；**进入管线后不再改写**（保持"请求"语义） |
| `Player` | `crit_chance_base` / `crit_multiplier` 是基础值，`crit_chance()` 走 `Stats`（Buff 可临时改）；`roll_damage()` 返回 `{amount, critical}` |
| `PlayerBullet` | `@export critical`，受击时连同伤害一起传给 `DamageInfo` |
| `DamageReceiver` | 把 `info.critical` 抄进 `DamageResult.critical` |
| `FloatingDamage` | 暴击时字号 +8、金色、文本追加「暴击」 |

结论：**攻击方决定、结果记录**这条链路不需要改管线协议，只在请求里加了一个字段。

### 11.2 吸血（只认实际掉血）

`Player.on_damage_dealt(result)`：`hp_damage <= 0` 直接返回；比例走 `lifesteal()`（`Stats` 的 `lifesteal` + 基础值）；`heal(round(hp_damage * ratio))`。
`PlayerBullet._try_hit` 在拿到 `DamageResult` 后回调攻击者，**攻击者必须先 `is_instance_valid`**（开枪后玩家阵亡的常见情况），无效就降级成"无攻击者"。

实测：真实掉 1 点 → 回 1 点；护盾挡下（`hp_damage == 0`）不回；无敌挡下不回；目标已死（`blocked_by == &"dead"`）不回；攻击者被释放不崩。

### 11.3 敌人护盾（通用组件复用）

新增 `scripts/combat/components/ShieldCharges.gd`（`class_name ShieldCharges`）：`defense_id = &"shield_charges"`、`charges`、`resolve_defense(info)` 有次数就返回 `info.amount` 并扣 1。
`EnemyChaser` 加 `@export starting_shield: int = 0`，出生时 `_attach_shield(n)` 动态建节点并塞进 `DamageReceiver.defenses`——**默认 0，不改现有难度**，留给带盾变体。

实测：追兵第一下被吸收、`blocked_by == &"shield_charges"`、血量不变；第二下正常掉血；无敌与护盾并存时先报 `invuln` 且不消耗次数，无敌清掉后由护盾接管；任意 `Node2D` 挂上同组件都能生效（不依赖 `PlayerFeatures`）。

### 11.4 协议暴露的不足（记录，不本轮改）

1. `resolve_defense(info) -> int` 只回吸收点数，**`blocked_by` 只记住最后一个防御组件**；出现"护甲减伤 + 护盾吸收"这类组合时表达不清。
2. `DamageInfo` 字段仍是普通 `var`，只读靠约定，编译期拦不住误改。
3. `DamageResult` 能区分"命中"（`hp_damage == 0` 且 `absorbed == 0`）与"造成生命伤害"，但"无敌挡"与"已死"只能读 `blocked_by` 字符串。

三条都不影响当前玩法；等真的出现多防御叠加或需要反伤/减伤链时再升级成 `DefenseResult` 协议。
