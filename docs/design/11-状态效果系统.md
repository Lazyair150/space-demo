# 11 · 临时状态效果系统（第一阶段）

日期：2026-11-19
范围：只做生命周期、撤回、定时、属性汇总；**不接入真实子弹伤害**，不引入命中上下文与事件总线。

---

## 0. 已锁定的所有权规则

```
GameState.attack_level        ← 永久攻击成长的唯一数据所有者
        ↓ attack_damage()
基础攻击力
        ↓ StatCalculator（只读基础值 + 汇总临时修正器）
最终攻击力
```

四条硬规则：

1. `GameState` 保存永久成长，Buff 系统**不写**它；
2. `StatCalculator` 不持有计时、不决定谁该存在，只做计算；
3. Buff 只登记临时修正器，到期由 `StatusEffectManager` 按 owner 撤销；
4. 修正器撤销后**重新计算**最终值，不做"当初加多少现在减多少"的补偿。

第一阶段攻击强化只验证"修正器能加、能撤、算得对"，子弹伤害接入留到第二阶段。

## 1. 模块与职责

| 文件 | 职责 | 明确不负责 |
| --- | --- | --- |
| `scripts/player/effects/BuffDefinition.gd`（`Resource`） | 静态规则：id、时长、叠加策略、修正器列表、tick 配置 | 不保存"谁身上还剩几秒" |
| `scripts/player/effects/BuffInstance.gd` | 运行时状态：剩余时间、层数、tick 进度；`on_apply/on_expire/on_tick` 空实现 | 不登记/撤销修正器 |
| `scripts/player/effects/PoisonBuffInstance.gd` | 中毒的 tick 行为（走目标 `take_damage`） | 不管理生命周期 |
| `scripts/player/effects/StatusEffectManager.gd` | 添加/移除/刷新/计时/按 owner 登记与撤销修正器/发信号 | 不计算属性 |
| `scripts/player/stats/StatCalculator.gd` | 基础值 + 修正器 → 最终值 | 不持有计时与永久成长 |

数据定义：`data/effects/haste.tres`（急速，`fire_rate ×0.6`，5 秒）、`attack_boost.tres`（攻击 ×1.5，10 秒）、`poison.tres`（每秒 1 点，5 秒，不叠层）。

场景挂载：`scenes/actors/Player.tscn` 新增 `Stats`（StatCalculator）与 `Effects`（StatusEffectManager，`stats_path = ../Stats`）。

## 2. 计算阶段（固定顺序）

```
基础值 → ① 固定值加算(FLAT) → ② 百分比乘算(MULT) → ③ 上下限钳制(bounds)
```

例（`tests/effects_smoke.gd` 实测）：基础 100，+10、+20，×1.5 ⇒ `(100+10+20)×1.5 = 195`；再加 `bounds[0,120]` ⇒ 钳制到 120。

阶段内加算/乘算可交换，故不需要排序；真正不可交换的"归零/覆盖"放在钳制阶段用 bounds 表达。

## 3. 叠加策略

`BuffDefinition.StackPolicy`：`INDEPENDENT / ADD_STACK / REFRESH / EXTEND / KEEP_STRONGEST / REPLACE / REJECT`。当前三张定义都用 `REFRESH`（重复施加刷时间、不叠层）。

**已知坑**：层数是乘到修正器值上的。`FLAT` 没问题；`MULT < 1`（例如急速 0.6）叠层会变成 1.2 反而更慢——已加 `push_warning` 拦截，不静默算错。

## 5. 两个实现中发现的真问题

1. **tick 不能按 `delta` 全量结算**：一次 `advance(3.0)` 而 Buff 只剩 1.5 秒时，朴素累加器会多打一次血。改成"按活过的时长 `min(elapsed, duration)` 与已触发次数取差"，并给 `duration_override` 单独存 `instance.duration`——否则 1.5 秒的毒会按定义里的 5 秒结算。
2. **`on_expire` 不负责撤修正器**：撤销由管理器在回调前完成，保证 `on_expire` 里看到的是"没有这个 Buff"的属性值（用户提的那条约束，实测有效）。

## 6. 拾取物与数值基础（第二阶段）

### 6.1 为什么先动数值

Phase 1 只证明了"修正器能加能撤"。但当时子弹固定 1 点伤害、追兵 1 血：
攻击强化 `×1.5` 在小数上等于没变化，玩家看不到任何区别。

所以这一阶段先给数值留出"能被感知"的差距：

| 对象 | 之前 | 现在 | 理由 |
| --- | --- | --- | --- |
| `EnemyChaser.max_hp` | 1 | 2 | 强化后 1 发打死，不强化 2 发；一枪之差能感觉到 |
| `EnemyShooter.max_hp` | 2 | 3 | 精英机（3/5/7）保持原样，普通射手介于两者之间 |
| 子弹伤害来源 | `GameState.attack_damage()` | `Player.attack_damage_int()` | 永久成长 + 临时修正一起进最终值 |

`attack_damage_int()` = `maxi(1, round(attack_final()))`：1 点基础下 `×1.5 = 1.5`，
若直接截断仍是 1，等于白吃——所以取整规则收敛在这一个函数里，并且**这是独立验收项**：
`pickup_smoke` 会真的开一枪，断言子弹 `damage == 2`，而不是只断言中间计算值。

### 6.2 通用拾取物

`scripts/pickups/BuffPickup.gd` + `scenes/pickups/BuffPickup.tscn`：

- 拾取物只持有一个 `BuffDefinition`，不 import 任何一种具体效果，也不碰 `fire_rate`；
- `body_entered` → 必须是 `player` 组 → 调 `grant_buff()` → **返回 null 就不吞掉胶囊**（宿主没有 Buff 系统时胶囊留在场上）；
- 成功施加才 `queue_free()`，并 emit `picked(definition)`；
- 15 秒没人捡自己消失，避免场上堆积；
- 通用白色胶囊 SVG（`assets/pickups/buff_capsule.svg`），按定义 id 用 `modulate` 染色，加一种 Buff 不需要新美术。

掉落入口挂在**敌人死亡信号**上，而不是新建一套掉落系统：

- `EnemyChaser` / `EnemyShooter` 各加 `signal died(at: Vector2)`，在两条致死出口（接触致死、血量归零）都 emit；
- `Spawner` 的 `pickup_scene` / `pickup_chance` / `pickup_effects` 三个导出项决定掉不掉、掉什么，概率默认 0.3；
- 胶囊加进 `Arena`，位置就是敌人死亡位置。

### 6.3 HUD

左下角一行「急速 4.8s　中毒 0.9s」：

- HUD 只读 `StatusEffectManager.active_entries()`（`{id,label,remaining,stacks}` 快照），不碰 `_instances`；
- 每 0.1 秒刷新一次，文本没变就不写，避免每帧重排；
- 订阅 `buff_added` 弹一次「获得 急速」，重复拾取走 REFRESH 不重复弹。
