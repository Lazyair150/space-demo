# 第三部分：理解 JarSystem.Core

## 10. Core 是什么

`JarSystem.Core` 是本次真正要复用的工业系统核心。

它是一个独立的 .NET 类库。

它不是 Godot 场景，不是 HTML 页面，也不是一个完整游戏。

它的价值是已经包含了工业世界的业务规则。

之前梳理过的主要模块包括：

|模块|主要职责|
|---|---|
|Config|配置|
|Domain|领域对象和数据|
|Orders|订单|
|Orders.Feasibility|订单可行性分析|
|Orders.Switching|订单切换|
|Solver|搜索和求解|
|Executor|原子操作执行|
|Commands|命令处理|
|Production|生产者、仓库和生产推进|
|Services|用例编排|
|Sessions|世界命令、会话和回放|
|Bootstrap / Abstractions|初始化和抽象接口|

这些模块的存在意味着 Godot 不应该重新实现它们。

## 11. 不要将 Core 内部结构复制成 Godot 模块

例如：

Core 已经有订单服务。

Godot 不需要再创建一套订单求解器。

Core 已经有生产逻辑。

Godot 不需要重新写一套生产算法。

Core 已经管理工业世界状态。

Godot 不需要自己保存另一份工业世界作为真实状态。

正确的职责关系：

```
JarSystem.Core
    |
    | 负责真实工业规则和状态
    |
    v
Godot 适配层
    |
    | 负责调用、转换和协调
    |
    v
Godot UI
       负责展示和输入
```

## 12. 建立 Core API 映射表

在 `space-demo` 中建立：

```
docs/industrial/02-core-api-map.md
```

调查以下能力：

|需要的能力|应该查找的内容|
|---|---|
|初始化|Core 构建入口、工厂、Bootstrap|
|查询世界|状态查询接口、快照 DTO|
|工作台操作|工作台服务或命令|
|创建订单|订单服务|
|删除订单|订单服务或命令|
|可行性分析|Feasibility 服务|
|执行订单|Executor、执行服务|
|推进世界|当前实际 Tick 入口|
|读取日志|日志或事件查询|
|存档|导出接口|
|恢复|导入接口|

每项都需要记录：

```

```

不要猜测方法名称。

不要仅凭类名推断方法行为。

不要把旧 Godot 宿主调用的方法当成最新 Core API 的唯一依据。

必须查看当前 Core 中的实际代码。

# 第四部分：确定最终 Godot 架构

## 13. 为什么采用混合架构

`space-demo` 原本主要使用 GDScript，而 JarSystem.Core 使用 C#。

不需要因此把整个太空游戏改写为 C#。

建议采用：

- GDScript：Godot UI、场景控制、运行生命周期。
    
- C#：JarSystem.Core 适配层。
    
- JarSystem.Core：工业规则和业务计算。
    

架构：

```
                 Godot 游戏
                     |
                     v
                Industrial UI
                 GDScript
                     |
                     v
              IndustrialRuntime
                 GDScript
                     |
                     v
               JarCoreBridge
                    C#
                     |
                     v
              JarSystem.Core
                    C#
```

## 14. 各层职责

### 14.1 UI 层

负责：

- 显示工作台。
    
- 显示订单。
    
- 显示仓库。
    
- 显示生产状态。
    
- 接收按钮输入。
    
- 显示分析结果。
    
- 显示操作反馈。
    

UI 不负责计算订单是否可行。

### 14.2 Runtime 层

负责：

- 初始化工业系统。
    
- 持有 Bridge。
    
- 管理工业生命周期。
    
- 推进工业逻辑时间。
    
- 处理场景切换。
    
- 提供当前工业状态。
    
- 管理暂停、恢复和保存。
    

### 14.3 Bridge 层

负责：

- 创建 Core。
    
- 调用 Core。
    
- 将 DTO 转换成 Godot 能使用的数据。
    
- 将 Godot 输入转换成 Core 所需参数。
    
- 返回统一操作结果。
    

### 14.4 Core 层

负责：

- 工业世界。
    
- 订单。
    
- 工作台。
    
- 求解。
    
- 命令。
    
- 执行。
    
- 生产。
    
- 工业规则。

## 16. C# 与 GDScript 的边界

C# Core 不能直接当成 GDScript 类型使用。

需要通过一个 Godot C# Node 脚本作为 Bridge。

GDScript 调用 Bridge 暴露的 Godot 方法。

建议让跨语言接口尽量使用 Godot 能处理的类型：

- bool
    
- int
    
- float
    
- String
    
- Array
    
- Dictionary
    
- Godot 对象
    

复杂 Core DTO 应在 C# 中转换，不要直接把任意 .NET 对象暴露给 GDScript。

另外，Godot C# 脚本和 GDScript 可以在同一个 .NET 项目中协作，但跨语言接口必须符合 Godot 的对象和 Variant 规则。

对于全局运行管理器，优先使用一个 GDScript Autoload 场景或脚本，再在其内部持有 C# Bridge 节点。不要未经验证就假定所有 C# 脚本都能像 GDScript 一样直接注册为 Autoload。

# 第五部分：实现 Core Bridge

## 17. Bridge 的意义

Bridge 是 Godot 与 JarSystem.Core 之间的适配层。

例如：

```
Godot 按钮
    |
    v
IndustrialRuntime
    |
    v
JarCoreBridge
    |
    v
JarSystem.Core
```

Godot 不需要知道 Core 内部有多少 Service、Command、Solver。

它只需要调用清楚的操作。

## 18. 先定义统一接口

建议 Bridge 提供以下接口：

|方法|作用|
|---|---|
|InitializeCore|初始化 Core|
|GetWorldSnapshot|查询世界状态|
|GetWorkshops|查询工作台|
|GetOrders|查询订单|
|CreateOrder|创建订单|
|DeleteOrder|删除订单|
|CheckOrder|可行性分析|
|ExecuteOrder|执行订单|
|TickOnce|推进一次逻辑 Tick|
|ExportWorld|导出世界状态|
|ImportWorld|恢复世界状态|

这些是 Godot 侧的接口约定，不是对 Core 现有 API 名称的断言。

Bridge 内部必须映射到真实 Core 方法。

## 19. Bridge 的工作流程

以创建订单为例：

```
Godot UI
    |
    v
IndustrialRuntime.create_order()
    |
    v
JarCoreBridge.CreateOrder()
    |
    v
转换 Godot 参数
    |
    v
调用 Core 订单服务
    |
    v
获取真实执行结果
    |
    v
转换结果 DTO
    |
    v
返回 Godot Dictionary
```

结果建议统一包含：

```
success
message
data
error_code
```

其中：

- success：操作是否成功。
    
- message：显示给用户的反馈。
    
- data：真实业务数据。
    
- error_code：可供程序判断的错误类别。
    

具体数据结构可以根据 Core 的真实返回值调整。

## 20. Bridge 不负责重新实现业务规则

例如：

错误：

```
Bridge
  |
  +-- 自己判断订单是否可行
  +-- 自己计算生产结果
  +-- 自己实现工作台规则
```

正确：

```
Bridge
  |
  +-- 传入订单参数
  +-- 调用 Core 可行性分析
  +-- 转换 Core 结果
  +-- 返回 Godot
```

Bridge 是适配层，不是第二个 JarSystem。

# 第六部分：将最新 Web 客户端重建为 Godot UI

## 21. 设计原则

Web 客户端是本次界面设计依据。

但 HTML、CSS 和 JavaScript 不是 Godot 的原生 UI 技术。

因此，不能简单地把 HTML 标签翻译成 Godot 节点。

应该先分析：

1. 页面信息层级。
    
2. 用户操作。
    
3. 数据来源。
    
4. 操作反馈。
    
5. 页面切换。
    
6. 状态更新。
    

再决定 Godot 节点结构。

## 22. Web 到 Godot 的映射

|Web 技术|Godot 实现|
|---|---|
|HTML 容器|Control、PanelContainer|
|Flex|HBoxContainer、VBoxContainer|
|Grid|GridContainer|
|Button|Button|
|Input|LineEdit、TextEdit|
|Select|OptionButton|
|列表|ItemList 或自定义容器|
|弹窗|AcceptDialog、ConfirmationDialog|
|DOM 更新|修改 Control 属性|
|JavaScript 事件|Signal 回调|
|CSS|Theme、StyleBox、Theme Overrides|
|页面切换|场景切换或面板显隐|

这只是功能层面的对应，不代表两种布局系统完全一致。

如果最新 Web 客户端采用不同的页面组织方式，应保留其真实功能，不要为了套用这个布局而删减信息。

## 24. 先制作静态 UI

第一轮只做：

- 场景结构。
    
- 控件布局。
    
- 视觉样式。
    
- 面板切换。
    
- 按钮响应。
    
- 输入交互。
    

数据暂时使用测试数据。

例如：

```
var test_orders = [
    {
        "id": "test_001",
        "name": "测试订单",
        "status": "等待执行"
    }
]
```

这只是 UI 测试数据。

它不能代替 Core 的真实订单状态。

第二轮才将 Bridge 返回的数据传给 UI。

## 25. UI 的状态所有权

必须区分：

|状态|所有者|
|---|---|
|工业订单真实状态|Core|
|工作台真实配置|Core|
|工业世界状态|Core|
|当前选中的订单|Godot UI|
|当前打开的面板|Godot UI|
|当前输入框内容|Godot UI|
|工业系统初始化状态|Runtime|
|玩家库存|太空游戏库存系统|
|产品是否已经发奖|游戏奖励系统|

UI 可以保存当前选择，但不能把自己保存的显示状态当成 Core 的真实状态。

# 第七部分：IndustrialRuntime 与后台生产

## 26. 为什么需要 Runtime

工业生产不能依赖工业界面是否打开。

如果 Runtime 放在工业场景内部，退出场景时它可能随场景一起销毁。

因此需要一个跨场景存在的运行管理器。

## 27. Runtime 的职责

IndustrialRuntime 负责：

- 初始化 Core。
    
- 持有 Bridge。
    
- 管理工业逻辑 Tick。
    
- 提供当前世界快照。
    
- 通知 UI 状态变化。
    
- 处理暂停和恢复。
    
- 保存和恢复工业状态。
    
- 管理运行期间的工业生命周期。
    

不负责：

- 订单求解。
    
- 生产算法。
    
- UI 绘制。
    
- 修改舰船属性。
    
- 重复实现 Core 规则。
    

## 28. 后台运行的场景

```
玩家打开工业界面
       |
       v
创建工业订单
       |
       v
开始工业运行
       |
       v
退出工业界面
       |
       v
进入战斗场景
       |
       v
Runtime 继续存在
       |
       v
Core 继续推进
       |
       v
重新进入工业界面
       |
       v
显示最新状态
```

## 29. Runtime 的时间管理

Godot 有 Frame 和 delta。

JarSystem 有自己的逻辑 Tick。

两者不能混为一谈。

```
Godot Frame
     |
     v
delta
     |
     v
时间累积器
     |
     v
达到 Tick 间隔
     |
     v
调用 Core Tick
```

例如：

```
var tick_interval := 1.0
var tick_accumulator := 0.0

func _process(delta: float) -> void:
    if not runtime_enabled:
        return

    tick_accumulator += delta

    while tick_accumulator >= tick_interval:
        tick_accumulator -= tick_interval
        tick_once()
```

这里每秒一次只是时间映射示例，不是 JarSystem 已经确定的规则。

真实时间间隔应该根据工业设计确定。

还要注意：

- 游戏暂停时是否推进工业时间，需要明确。
    
- 游戏失去焦点时是否推进，需要明确。
    
- 窗口最小化时是否推进，需要明确。
    
- 长时间卡顿后是否补足多个 Tick，需要明确。
    
- 必须避免单帧大量补算导致卡死。
    

如果 Core 已经提供统一 Tick 入口，就让 Core 管理内部步骤。

Godot 不应自行拆开 Core 的生产流程。

## 30. 重要：现有 Core 和过程系统设计规格的区别

之前研究过的 JarSystem 过程系统设计提出了：

- State
    
- Rule
    
- Modifier
    
- Process
    
- Step
    
- Tick
    
- Event
    
- Guard
    
- Outcome
    
- Journal
    
- Milestone
    

以及 Process 状态机：

```
Created
   |
   v
Ready
   |
   v
Running
   |
   +------> Succeeded
   |
   +------> Blocked
   |           |
   |           v
   |         Running
   |           |
   |           v
   |         Failed
   |
   +------> Aborted
```

设计规格还提出：

```
每个 Tick：

1. 事件注入
2. Modifier 更新
3. Process 推进
4. 世界产出与流入
```

但是，这些属于过程系统设计规格。

之前检查过的设计文档明确指出：订单执行目前是同步瞬时的，`ExecutionLogEntry` 是事后日志，`SolverStepDto` 是事前预测路径，它们不能直接当成正在执行的 Process 状态。

因此，必须先检查当前 Core 代码。

不能直接认为：

- 已经存在完整 Process Scheduler。
    
- 已经存在可中断订单。
    
- 已经存在跨 Tick 执行。
    
- 已经实现 Blocked 等待。
    
- 已经实现 Process Journal。
    

如果这些功能尚未落地，就要作为独立的 Core 开发阶段处理。

### 推荐实施策略

第一阶段：

- 先使用当前 Core 已经存在的能力。
    
- 订单仍然按照当前真实行为执行。
    
- 世界生产按照当前真实 Tick 机制推进。
    
- Godot 只负责调用。
    

第二阶段：

- 如果确实需要订单时间化执行，再实现 Process 系统。
    
- 先完成 Core 的 0 Tick 等价版本。
    
- 再实现跨 Tick。
    
- 再实现中断、等待和恢复。
    
- 最后让 Godot 展示 Process 状态。
    

不要为了 Godot 界面而提前重构 Core。

# 第八部分：游戏资源与工业资源桥接

## 31. 为什么需要资源适配层

太空游戏和 JarSystem 拥有不同的资源模型。

太空游戏可能有：

```
矿石
燃料
电子元件
稀有晶体
```

JarSystem 有自己的：

```
仓库
容器
液体
工作台
订单材料
```

不能因为它们都是资源，就直接合并成一套数据结构。

## 32. 资源映射

建立：

`docs/industrial/04-data-mapping.md`

记录：

|游戏资源|工业资源|转换方式|
|---|---|---|
|矿石|对应工业原料|根据配方|
|燃料|对应工业消耗品|根据配方|
|电子元件|对应工业组件|根据配方|
|工业产品|游戏强化材料|根据奖励映射|

具体映射必须根据真实资源定义确定。

## 33. IndustrialInventory

它负责：

1. 读取玩家库存。
    
2. 检查材料数量。
    
3. 扣除投入工业的游戏资源。
    
4. 向 Core 转移工业材料。
    
5. 接收工业产品。
    
6. 将工业产品转换为游戏资源。
    
7. 记录资源转移结果。
    

它不负责重新实现工业仓库规则。

## 34. 防止重复扣除

资源转移不能简单地分成两次无关联操作。

例如：

```
玩家有 100 矿石
     |
     v
准备投入 20 矿石
     |
     v
检查材料是否足够
     |
     v
生成转移操作 ID
     |
     v
扣除游戏库存
     |
     v
向 Core 提交材料
     |
     v
记录转移结果
```

如果 Core 接收失败，不能直接丢失材料。

应设计明确的失败恢复机制。

如果无法实现真正的跨系统事务，可以使用带唯一 ID 的转移记录和补偿操作。

核心要求是：

**同一笔资源转移只能成功一次，失败时也必须能够解释和恢复。**

# 第十部分：存档与恢复

## 39. 第一版存档规则

- 游戏运行期间工业持续推进。
    
- 退出游戏前保存。
    
- 重新进入时恢复。
    
- 游戏关闭期间不生产。
    
- 不计算离线时间。
    

## 40. 需要保存的数据

|数据|归属|
|---|---|
|工业世界|Core|
|工作台状态|Core|
|订单状态|Core|
|生产状态|Core|
|工业逻辑 Tick|Core 或 Runtime，依据真实实现|
|游戏库存|太空游戏|
|产品领取记录|游戏奖励系统|
|资源转移记录|游戏工业适配层|

## 41. 保存流程

```
游戏退出
    |
    v
停止工业 Tick
    |
    v
请求 Core 导出状态
    |
    v
保存 Core 状态
    |
    v
保存游戏库存
    |
    v
保存产品领取记录
    |
    v
保存资源转移记录
    |
    v
完成存档
```

## 42. 恢复流程

```
游戏启动
    |
    v
读取游戏存档
    |
    v
初始化 Core
    |
    v
导入工业世界
    |
    v
恢复游戏库存
    |
    v
恢复奖励记录
    |
    v
恢复资源转移记录
    |
    v
验证数据一致性
    |
    v
开始工业 Tick
```

不要直接保存 Core 对象本身。

必须使用 Core 已经提供的序列化或导出机制。

如果当前 Core 没有提供合适的存档接口，就应该先明确设计并实现 Core 的存档接口，而不是让 Godot 自己猜测 Core 内部对象结构。

12. 不在第一版加入离线生产。
    

## 58. 关于模块拆分

不要因为存在一个状态，就立即建立一个 Manager。

例如：

- 有订单状态，不一定需要 OrderStateManager。
    
- 有生产状态，不一定需要 ProductionStateManager。
    
- 有工作台选择，不一定需要 WorkshopManager。
    
- 有日志，不一定需要独立的日志系统。
    

应该先分析：

1. 状态由谁拥有？
    
2. 谁可以修改状态？
    
3. 修改状态的事件是什么？
    
4. 是否存在独立的业务规则？
    
5. 是否有复杂的生命周期？
    
6. 是否有必要单独管理？
    

只有职责确实复杂，才拆分模块。
