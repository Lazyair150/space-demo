# Space 工程编码与架构规范

状态：本仓库工程规范（适用于 GDScript、C#、Godot 场景资源和跨仓库协议）。

本规范参考《阿里巴巴 Java 开发手册》的分类方法和质量原则，但不是 Java 规则的逐条移植。阿里手册覆盖编程规约、异常与日志、单元测试、安全、工程结构和设计规约，并按强制、推荐、参考分级。本项目采用同样的分级方式，按 Godot/C# 的实际语义落地。

## 1. 规则等级

- **MUST（强制）**：违反会导致状态错误、数据损坏、跨模块耦合或不可维护风险；合并前必须修复。
- **SHOULD（推荐）**：默认遵守；偏离时应在代码注释或架构记录中说明理由。
- **MAY（参考）**：按具体场景选择，不为形式统一牺牲清晰度或性能。

## 2. 命名、格式与文件组织

### GDScript
- MUST：文件名、类名、场景资源路径保持一致且语义明确；类名使用 PascalCase，函数/变量使用 snake_case，常量使用 UPPER_SNAKE_CASE。
- MUST：所有从 Variant、Dictionary.get()、未类型化容器或条件表达式得到的值，在参与类型敏感操作前必须显式标注类型或完成类型检查。不得依赖隐式推断猜测类型。
- MUST：公开方法、跨场景调用方法和生命周期入口写明用途、调用时机、失败语义；复杂状态转换补充前置条件。
- SHOULD：优先使用有类型的参数、返回值、Array 和 Dictionary；动态 call() 只允许用于确实需要的动态边界，并集中封装。
- SHOULD：单个函数只负责一个可描述的动作；长流程拆成校验、准备、提交、回滚阶段。
- MUST：信号连接在重复进入场景时不得重复注册；退出场景时释放临时连接、Timer、Callable 和节点引用。

### C#
- MUST：启用 Nullable Reference Types；公共 API 明确参数、返回值和异常/失败语义。
- MUST：覆写方法使用 override；静态成员通过类型访问；避免无必要的动态类型和 Godot Variant 往返。
- SHOULD：遵守 .NET 命名约定：类型/公共成员 PascalCase，局部变量/参数 camelCase，私有字段使用项目统一的下划线前缀。
- SHOULD：异步、事件和资源释放路径明确所有权；Godot Node 生命周期由 Godot 管理，不与 IDisposable 所有权混淆。
- MUST：C# Bridge 只承担 Godot 适配、参数转换、生命周期和错误映射，不复制 Core 的领域规则。

### 通用
- MUST：禁止提交临时调试代码、废弃文件、未使用资源和秘密/本机路径。
- SHOULD：避免“万能管理器”、无边界静态状态、缩写不明的变量名和跨层反向依赖。
- SHOULD：注释解释原因、约束和非显而易见的决策，不重复逐行代码。

## 3. 分层与依赖方向

依赖方向必须保持单向：

UI / Scene → Application Flow / Controller → Space Domain / Runtime → WorldV2 Host Adapter → Jar Core

- **UI/Scene**：呈现状态并转发玩家意图；不拥有资源守恒、求解器、战斗时钟或跨场景导航决策。
- **Application Flow**：唯一管理根场景导航和应用屏幕状态；战斗生命周期状态由 GameFlow 维护。
- **Space Domain**：拥有飞船、成长、技能效果、战斗、关卡、生产设备及 Space 侧持久化语义。
- **WorldV2 Host Adapter**：负责 Core Runtime 生命周期、命令/快照桥接、时间步协调和故障边界。
- **Jar Core**：唯一拥有 Jar 规则、工作台规则、订单可行性/准入/执行、预留、逻辑时间和资源账本。

MUST：Space 不复制 Jar Core 的规则、求解器、资源扣减或订单准入算法。发现需要重复实现时，应先扩展 Core 的稳定接口。

MUST：一个领域事实只能有一个权威所有者。HUD、预览和 ViewModel 都是派生视图，不得成为第二份可写真相。

## 4. 状态、生命周期与事务

- MUST：状态机使用明确枚举/状态值和合法转换；禁止用多个互相矛盾的 bool 拼出隐式状态机。
- MUST：状态转换先验证前置条件，再执行副作用；失败时要么保持原状态，要么执行完整回滚。
- MUST：场景退出、战斗结束、故障和取消路径幂等；重复调用不得重复释放、重复结算或误伤新会话。
- MUST：临时对象有唯一所有者和明确释放时机；Autoload 不得持有已退出场景的强引用。
- MUST：资源交接、存档快照和结算遵循“完整预检 → 构造候选 → 原子提交 → 发布结果”；不得暴露半完成状态。
- MUST：战斗时间只有一个权威推进路径；暂停必须同时关闭 Space 与 Jar 的推进门，不能用 Engine.time_scale 或隐藏节点代替生命周期控制。
- SHOULD：所有跨场景命令携带稳定身份/版本；异步结果返回时校验身份，拒绝过期结果。

## 5. 数据契约、快照与序列化

- MUST：跨 Core/Space 的字段名、字段顺序、数组顺序、默认值、整数/浮点语义、空值语义和版本升级策略均视为协议的一部分。
- MUST：不得依赖不同语言的默认 JSON 序列化行为来计算同一指纹。指纹必须有明确的规范化输入；修改协议时同步修改双方测试向量。
- MUST：冻结快照创建时深拷贝可变输入；读取时不得泄漏内部可变引用。
- MUST：先校验 schemaVersion 和必需字段，再读取/转换数据；不得将缺失字段静默替换成可能改变业务含义的默认值。
- MUST：未知 schema、重复身份、非法数值、非规范 ID 和不匹配指纹必须显式拒绝，并提供可定位的错误原因。
- SHOULD：为每个跨语言协议维护至少一组固定输入、期望规范 JSON 和期望 SHA-256 的 golden vector。
- SHOULD：时间、资源数量和成本优先使用明确的整数单位；浮点只用于确有连续量需求的值，并规定精度/范围。

## 6. 错误处理与日志

- MUST：预期业务拒绝使用明确返回值/错误列表；异常或引擎故障不得伪装成普通“未选择”。
- MUST：捕获异常时保留上下文，不得吞掉异常后继续运行一个部分初始化对象。
- MUST：错误消息包含子系统、操作、对象身份/版本和失败原因；不得输出密钥、令牌或敏感存档内容。
- SHOULD：使用统一前缀，例如 [Hangar]、[Game]、[WorldV2ShipHost]；高频帧循环不得逐帧打印日志。
- SHOULD：同一故障只在责任边界记录一次完整错误；上层可补充上下文，不重复堆栈。

## 7. 集合、资源与性能

- MUST：修改集合前明确其所有权；对外快照使用深拷贝或不可变表示。
- MUST：遍历时不得在同一集合上做会改变索引/枚举器语义的结构性修改。
- MUST：字典读取后检查类型和必需键；禁止把 Variant 容器直接当作强类型数据使用。
- SHOULD：避免每帧创建大型 Dictionary/Array、重复解析 JSON 或重复计算指纹；可在边界处缓存已验证的不可变结果。
- SHOULD：缓存必须有明确失效条件，不得让缓存绕过权威状态。

## 8. 测试规范

测试分层执行，不能用一个成功的构建替代行为验证：

1. **静态/导入检查**：Godot headless editor import、GDScript parse、C# build。
2. **领域单元探针**：边界值、无效输入、重复请求、状态转换、资源守恒。
3. **跨仓库集成探针**：固定 Core SHA、Bridge build、协议 golden vector、Runtime 生命周期。
4. **场景/流程探针**：真实调用导航和按钮动作，验证暂停门、Host 生命周期、场景退出及重新进入。
5. **人工 GUI 验收**：真实窗口布局、OptionButton 事件、输入焦点、交互可用性。CI 不能替代这一层。

- MUST：探针有确定性输入、明确断言和唯一完成标记；失败时退出非零。
- MUST：覆盖成功、拒绝、重复、故障、恢复、退出和资源释放路径。
- MUST：固定 Seed 的随机测试记录 Seed、样本数和失败样本；禁止只记录“随机通过”。
- SHOULD：测试名描述行为和边界，不只描述实现函数名。
- SHOULD：每次修复一个生产缺陷，同时增加能在 CI 重现该缺陷的回归测试。
- MUST：CI 绿色只代表该 SHA 和该工作流覆盖的内容通过，不代表 GUI、所有平台或未执行路径已通过。

## 9. 安全与配置

- MUST：不把用户输入直接拼接成文件路径、命令或资源路径；校验资源 ID、版本、数量和数值范围。
- MUST：配置文件加载失败必须显式失败，不得悄悄回退到 Sandbox/默认世界，除非调用方明确选择开发模式。
- MUST：生产启动使用机库冻结的配置快照；Sandbox 入口仅供显式开发/探针路径使用。
- MUST：持久化数据按 schema 版本验证；升级/迁移幂等，不覆盖已有合法进度。
- SHOULD：对日志、错误面板和诊断快照做最小化输出。

## 10. 评审清单

每个较大改动至少回答：

- [ ] 是否只有一个权威数据所有者？
- [ ] 是否保持 UI、应用层、领域层、Host、Core 的依赖方向？
- [ ] 是否定义输入、输出、失败语义和状态前置条件？
- [ ] 是否处理重复调用、退出、故障和回滚？
- [ ] 是否对 Variant、空值、集合和数值边界进行显式校验？
- [ ] 跨仓库协议是否有版本、规范序列化和固定测试向量？
- [ ] 是否新增/更新行为回归测试？
- [ ] 是否在文档中说明未覆盖的人工验收或平台限制？
